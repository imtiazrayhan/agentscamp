An attractive generated preview does not establish that a mesh will work in the application where someone needs it. Review the exported asset against a named use, measurable requirements, a real technical report, and human observations in the target viewer. The final decision belongs to the asset owner and applies to a particular version.

This workflow is for a visual asset handoff. It does not establish manufacturing suitability, medical use, or structural performance. After geometry review, use the [PBR texture import workflow](/guides/design/review-ai-pbr-texture-imports) to check the material setup separately.

## Write an acceptance brief before generation

Name the target application and version, intended use, export format, scale convention, orientation, and owner-set limits. State what must be measured and what a person must inspect. A static display prop and an animated character require different evidence; do not invent a universal “production ready” checklist.

Turn vague requirements into reviewable questions. Instead of “lightweight,” write the approved triangle budget and the method used to count it. Instead of “looks right,” name the viewing angles, intended silhouette, and reference supplied by the owner. If a budget or reference is missing, leave the corresponding decision unresolved.

Assign an owner for acceptance and a person or tool capable of actual inspection. A text assistant can organize supplied reports. It cannot determine topology, normals, or geometry from a binary mesh it cannot parse, and a filename does not prove an asset’s contents.

## Preserve the generation and export history

Record the generation task ID, source prompt or image reference, selected output, export ID, file names, and versions. Keep original downloads unchanged. Work on a clearly identified copy and document any edits or conversions before inspection.

[Meshy](/tools/meshy) is one generation option. Its [API documentation](https://docs.meshy.ai/en/api/text-to-3d) describes preview and refine tasks returning model outputs. Retain the actual output you received; do not equate a preview image with the exported mesh or assume every task returns the same files.

[Meshy’s pricing page](https://www.meshy.ai/pricing) distinguishes web plans from API credits. Confirm the export options available in the workflow you use. A pricing tier or successful download is not evidence that the resulting geometry meets your handoff brief.

## Inspect the asset in the actual target

Open the exact export in the chosen application. Record the application version, importer settings, and any warnings. If import fails, preserve the failure and stop that acceptance path. Do not describe a source preview as a successful target import.

Obtain a technical report generated by an appropriate inspection tool or a qualified human. The report should identify the inspected file and method, list the requested measurements, and distinguish counts before and after any conversion. Record what it did not test. A report containing one polygon count is not a complete inspection of the asset.

Have a person review the actual model from the agreed views. Capture notes and screenshots with view references: front silhouette, rear surface, underside, or close-up of a specific region. Distinguish a visible artifact from its suspected cause. “Dark patch on the rear panel in view R2” is evidence; “broken normals” requires a suitable inspection or a verified diagnosis.

[UV mapping](/glossary/uv-mapping) connects texture placement to the mesh version. If the handoff includes textures, register their relationship to the inspected geometry. The [glTF specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html) defines texture-coordinate use for that format; another chosen format needs its own documented conventions.

## Worked example: a fictional lantern display prop

This example is invented, including its report and viewer notes. The owner wants a lantern for a static promotional render and sets a budget of 12,000 triangles. The export is `lantern-v3`, and the supplied technical report identifies that file and reports 18,000 triangles.

The human viewer note says the front silhouette matches the approved reference. It also records a dark patch on the rear panel, with a screenshot reference. Neither observation changes the triangle requirement.

| Requirement | Supplied evidence | Review state |
| --- | --- | --- |
| At most 12,000 triangles | Technical report: 18,000 | Fails owner budget |
| Approved front silhouette | Human note and front-view screenshot | Meets this visual check |
| Rear surface appearance | Dark patch recorded in rear view | Needs investigation |
| Normal behavior | No suitable report supplied | Untested |

A draft claiming “asset approved because it looks correct” ignores the measured failure. A draft claiming “normals are clean” invents a result. Correct both and send the owner separate options: approve a revised budget, request an edited version for a fresh report, or reject this export.

If an edit produces `lantern-v4`, repeat the relevant measurements and views on v4. Keep v3’s findings in the history. Do not attach v3’s silhouette approval to v4 without checking whether the edit changed it.

## Make the evidence table the handoff

Use the [3D asset handoff sheet](/skills/design/3d-asset-handoff-sheet) to organize the brief, exact files, reports, viewer notes, settings, and owner decisions. Link each claim to its evidence. Mark unsupported properties untested rather than replacing them with an AI confidence estimate.

Separate fix requests by evidence type. A geometry budget failure needs a new measured result after editing. A visible artifact needs actual target-view confirmation after correction. A missing report needs inspection, not rewritten prose. This separation prevents a cosmetic change from being mistaken for resolution of a technical failure.

Include a versioned recheck list. State which requirement changed, which export is affected, and which previous evidence is now stale. Preserve importer warnings and unsuccessful attempts, since they may explain why a handoff works in one environment and fails in another.

## Obtain a bounded owner decision

The owner records accept, fix, reject, or unresolved for each requirement, then decides the overall handoff. Acceptance should name the file version, target environment, intended use, and any explicitly accepted exception. Do not infer approval from silence or from a successful render of one angle.

Completion means the recipient can reproduce the import and assess the same evidence. Keep the original asset, inspected version, report references, viewer observations, and approval together. If the target use or application changes later, the earlier approval remains a historical decision, not a guarantee for the new context.
