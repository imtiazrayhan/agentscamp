Choose Microsoft 365 Copilot or ChatGPT for work by testing three things: whether your approved workspace can use the required evidence, whether the result lands in a useful format, and whether a teammate can review it. If those fail, fluent writing will not rescue the workflow. Start with the task your team repeats, rather than a general claim that one assistant is smarter.

For an Office-based team, begin with the Copilot experience available in the relevant app. For a task built around a supplied source pack and a standalone deliverable, include your approved ChatGPT workspace in the pilot. These are starting points to investigate, not product rankings. A company may reasonably choose different assistants for an email reply, a report and a presentation.

## Compare the experience you can actually open

As of October 2026, Microsoft is transitioning the name Microsoft 365 Copilot to Microsoft Copilot. Check the workplace product and account behind the label. [Microsoft naming and protections documentation](https://learn.microsoft.com/en-us/copilot/privacy-and-protections).

Use this compact access map before running a comparison:

| Experience | Documented context or role |
| --- | --- |
| Copilot web or app chat | Web, supplied material and supported app context. |
| Eligible Outlook chat | Limited mailbox-related organizational context. |
| Full licensed Copilot grounding | Broader organizational work context through Work IQ. |
| ChatGPT Chat | Questions and short drafts. |
| ChatGPT Work | Substantial deliverables using available files, plugins and approved tools. |

The Microsoft rows describe distinct context routes; tenant, client and license matter. Existing permissions apply. [Microsoft Copilot Chat overview](https://learn.microsoft.com/en-us/copilot/overview). The ChatGPT rows describe intended uses, with desktop capabilities depending on available tools. [Get started with ChatGPT Work](https://learn.chatgpt.com/docs/get-started-with-work).

For ChatGPT, integration availability, role access, authorized account, allowed actions and accessible resources are separate. Shared or agent-owned credentials can differ from the requester's own permissions; individual confirmation is not required for every action. Plan, configuration and rollout affect availability. [ChatGPT Work overview](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-overview). Write down the actual account and resources used in your test.

Installing or enabling a plugin alone does not authorize an external account. Check role, action and source-service permissions separately. [Plugin controls](https://learn.chatgpt.com/docs/enterprise/apps-and-connectors). A plugin icon is not evidence that a particular folder can be read or that an intended write is allowed.

## Define a workplace task before choosing a tool

“Help our team with AI” is too broad to evaluate. “Prepare the October staffing decision for the operations lead” gives you a source set, an audience and an observable result. Use this requirements sheet for one task:

| Requirement | Write down | What the reviewer checks |
| --- | --- | --- |
| Evidence | Named files, messages and versions | The result uses those sources, rather than a similarly named file. |
| Source location | Supplied copy or approved connected location | Required evidence was available through the tested route. |
| Intended readers | Decision owner and reviewers | Sensitive detail and explanations fit the audience. |
| Destination | Email draft, document or presentation | The output opens where the team will use it. |
| Editability | Sections, tables or slide objects that need revision | A colleague can make the expected changes. |
| Missing information | Questions that must remain unresolved | The draft does not fill gaps with plausible guesses. |
| Authority | Who may recommend, approve or communicate | Proposals are not presented as approved commitments. |
| Actions | Draft only, or a specifically authorized action | The workflow stays within the agreed task. |

Choose a small source pack that the reviewer understands. It should contain a real distinction the output must preserve, such as a current policy alongside a proposed change. Avoid an easy demonstration whose only requirement is pleasant prose. You need to learn whether the assistant can assemble evidence into a usable decision aid.

## Worked example: a regional repair-service review

This is a fictional example for planning a pilot, not an output produced by either product. A regional repair service needs a one-page October staffing brief. Its operations lead provides three invented sources:

- `service-metrics.csv`, a frozen September export with dated service records and named columns.
- `dispatch-policy.docx`, the current approved policy with a version date and staffing approval rules.
- A supervisor message proposing a different weekend roster, with author and date preserved.

The CSV supplies observations. The policy controls what can be committed. The message supplies a proposal, not an approval. That distinction is more useful to test than whether either assistant writes an energetic introduction.

The desired brief has four sections: observed service patterns, applicable policy, proposed staffing changes and unresolved questions. Each factual statement points to a row, section or message. The operations lead must be able to remove the proposal without altering the observations, and identify any question that blocks a staffing decision.

For example, a supervisor's sentence “we should try an extra weekend shift” belongs under proposed changes. It does not establish that a shift has been funded, approved or assigned. If the policy requires an approval that is absent from the pack, the brief should ask for it. Supply that authority rule in the instructions instead of expecting the assistant to infer your internal process.

Use a common pilot prompt, adapted to the available surface:

```text
Task: draft a staffing-review brief for our fictional repair region.
Use only the three named sources supplied for this pilot.
Separate observed metrics, current policy, proposed changes and unknowns.
For each factual claim, name the source and row/section/message.
Do not infer approved staffing changes from a supervisor's suggestion.
Return a one-page draft and a source-check table. Do not send or update systems.
Reviewer: operations lead. Ask if an essential source is unavailable.
```

Those instructions describe the desired result and task boundary. They do not technically enforce permissions or guarantee compliance. The reviewer still checks the sources and the draft; the workspace's actual controls govern available actions.

## Run two separate checks

First, supply the same approved copies to each authorized experience and request the same brief. Keep the source versions, task and review standard consistent. This isolates the work of interpreting the source pack and producing the deliverable from the separate question of finding it.

Second, test retrieval of one known source from the integration your team expects to use. Name the precise resource and verify it independently. Do not expand the test to every company system. If a file cannot be retrieved, record which account, surface and route were used. That is a workflow finding; it does not establish that the assistant would misunderstand a file supplied another way.

Record results without inventing a winner score:

| Task / surface / account | Source and version | Retrieved? | Factual correction | Output location / teammate access | Open question / next action |
| --- | --- | --- | --- | --- | --- |
| Staffing brief / tested app / named account | Exact policy version | Record observed result | Record required correction | Open and inspect the actual artifact | Name the owner of the unresolved issue |

Keep the original output beside the corrected version. “Needed review” is too vague: record whether the correction concerned a source, an arithmetic error, an unsupported commitment or the file format. Open the source behind each important claim. Reproduce any calculation using the source rows and stated denominator. Then have a colleague open the delivered artifact through the intended sharing route.

## Diagnose the failure before changing products

| What happened | Next check |
| --- | --- |
| A colleague gets different context | Compare account, app surface and configuration. |
| A required file is absent | Verify the exact resource and authorized connection. |
| The evidence is present but the statement is wrong | Inspect the supporting passage and refine the source or authority instruction. |
| The prose is useful but the output cannot be edited | Specify the destination and expected editable elements, then inspect the next artifact. |
| A suggestion becomes an approved commitment | Return it to the proposal section and ask the decision owner. |
| The source pointer leads nowhere | Treat the claim as unverified until the reviewer finds supporting evidence. |

An access problem may need an administrator; a wrong statement needs evidence review; a poor deliverable may need a clearer format brief. Recording the difference prevents a team from changing tools to solve an instruction problem, or rewriting prompts to solve an unavailable resource.

Choose the experience that completes the recurring task under your team's controls with an inspectable result. Keep a second workflow only when it solves a distinct need you can name.
